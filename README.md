## Даалгавар 2: Тест дизайн (Лекц 5-ын 5 алхам)

**1. Бие даан тестлэгдэх функц:** `POST /registrations` — оюутныг хичээлд бүртгэх. PUT endpoint-ууд нь зөвхөн setup (Initialization).

**2–3. Сонголтууд ба төлөөлөх утгууд (эквивалент ангиуд):**

| Сонголт | Эквивалент анги → төлөөлөх утга |
|---|---|
| studentID-гийн хүчинтэй байдал | **идэвхтэй** (`status:"active"`, эсвэл status орхисон) · **идэвхгүй** (`"inactive"`) · **байхгүй** (PUT хийгээгүй ID, ж: `B00-NOT-EXIST`) · **талбар дутуу/хоосон** (→ 400) |
| Оюутны үзсэн хичээлүүд (coursesTaken) | **урьдачийг бүгд агуулсан** (`["CS201"]`) · **хоосон** (`[]`) · **зарим нь** (`["CS201"]` vs урьдач `[CS201, CS202]`) |
| courseID-гийн хүчинтэй байдал | **байгаа** (PUT хийсэн) · **байхгүй** (`CS999-NOT-EXIST`) · **талбар дутуу** (→ 400) |
| Хичээлийн урьдач нөхцөл (prerequisites) | **байхгүй** (`[]`) · **нэг** (`["CS201"]`) · **олон** (`["CS201","CS202"]`) |
| Хүсэлтийн формат | **зөв JSON** · **буруу JSON** (→ 400 ERROR_BAD_JSON) |

**Боломжгүй хослолууд (тестлэх шаардлагагүй гэж хассан):** байхгүй оюутан + "урьдач хангасан/хангаагүй" (байхгүй оюутанд coursesTaken гэж байхгүй); байхгүй хичээл + "урьдач бүгд/зарим нь" (байхгүй хичээлд урьдач байхгүй); урьдачгүй хичээл + "урьдач дутуу" (дутах зүйл байхгүй); талбар дутуу (400) + аливаа бизнес дүрэм (сервер талбар шалгаад шууд буцаана).

## Даалгавар 3: Collection

`lab05-collection.json` — 14 тест тус бүр **бие даасан**: өөрийн оюутан/хичээлийг өвөрмөц ID-аар (`B23-S05`, `CS313-S05` …) PUT-ээр өөрөө бэлддэг тул дараалал болон бусад тестээс хамаарахгүй, давтан ажиллуулахад ч PASS. Oracle бүр **статус + result** хоёуланг шалгана; ERROR_PREREQUISITES-д `missing` массивыг, 201-д `registrationID` нь **тоо** эсэхийг (яг утгыг биш — сервер in-memory тул хуримтлагддаг) шалгана. Setup PUT бүрт `200` oracle бий. `{{baseUrl}}` = `http://localhost:3000` collection variable.

DOWN үед assertion-ууд fail болсон нь функц буруу ажилласныг биш, холболт байхгүйг харуулна.

## Олдсон согогууд

Тест дизайны явцад (сонголт бүрийн "сонирхолтой" утгыг туршихад) дараах согог олдсон. Үндсэн collection-ийг ногоон байлгах үүднээс тэдгээрийг тусдаа `lab05-defects.json`-д **зөв гэж үзэж буй хүлээгдэх үр дүнгээр** бичсэн (тиймээс FAIL болдог):

1. **`courseID: "toString"` серверийг унагадаг (DoS).** `courses` нь энгийн JS объект тул `courses["toString"]` нь `Object.prototype.toString` функцийг буцаана → `course.prerequisites` undefined → `.filter` дээр `TypeError` → барьж аваагүй exception Node процессыг зогсооно. Дараагийн бүх хүсэлт ECONNREFUSED. `constructor`, `valueOf`, `hasOwnProperty` зэрэг нэр ч мөн адил.
2. **`studentID: "toString"` / `"__proto__"` (байхгүй оюутан) → `ERROR_NO_STUDENT` биш `ERROR_INACTIVE_STUDENT` буцаана** — ижил шалтгаан (prototype-ийн гишүүнийг оюутан гэж үзэж, `status` undefined ≠ "active").
3. **Давтан бүртгэл хориглогдоогүй** (S14): ижил оюутан ижил хичээлд дахин 201 авна. Спецификацид заагаагүй тул согог гэхээсээ асуулт гэж тэмдэглэв.

**Засах санал:** `students`/`courses`-ийг `Map` эсвэл `Object.create(null)` болгох, эсвэл `Object.hasOwn(courses, courseID)`-ээр шалгах.

`results/newman-defects.txt`: assertions failed 7 / 7, requests failed 5 (`socket hang up` → дараа нь ECONNREFUSED), exit 1.

Дизайны 5 алхмаас хамгийн их бодол шаардсан нь 2–3 дахь алхам буюу сонголтуудыг тодорхойлж, эквивалент анги болгон хуваах байсан: "оюутан" гэдэг нэг сонголт мэт боловч байгаа эсэх, идэвхтэй эсэх, үзсэн хичээл гэсэн гурван бие даасан хэмжээс болж задарсан. Зааварт давхар алдааны дарааллыг заагаагүй байсныг S07–S09 тестээр тогтоосон: сервер оюутныг хичээлээс өмнө шалгадаг. Collection-ийн 14 тест тус бүр өөрийн өвөрмөц ID-тай setup-аа хийдэг тул бие даасан бөгөөд давтан ажиллуулахад ч 57 assertion бүгд PASS байсан; registrationID-ийн яг утгын оронд тоо эсэхийг шалгасан нь in-memory серверийн хуримтлалд тэсвэртэй болгосон. Зориуд буруу oracle-той FAIL collection exit code 1 буцааж, CI quality gate хэрхэн ажилладгийг харуулсан бол сервер унтраастай DOWN ажиллуулалт ECONNREFUSED-ээр интерфейсийн алдаа ба oracle-ийн алдааны ялгааг тод харуулсан. Хамгийн чухал үр дүн нь тестүүд жинхэнэ согог олсон явдал: `courseID: "toString"` илгээхэд сервер бүхэлдээ унадаг (DoS), `studentID: "toString"` нь байхгүй оюутныг идэвхгүй гэж буруу ангилдаг. Энэ хоёр согогийг "хүчинтэй/хүчингүй ID" ангийн дотор JavaScript-ийн онцлогтой холбоотой онцгой утгыг санаатайгаар туршсаны дүнд олсон нь эквивалент ангийг зөвхөн бизнесийн утгаар бус, хэрэгжүүлэлтийн технологийн эрсдэлээр ч бодох хэрэгтэйг харуулсан. Мөн давтан бүртгэлийг сервер хориглодоггүйг S14 илрүүлсэн ч спецификацид заагаагүй тул үүнийг шаардлагын асуулт гэж тэмдэглэв.
